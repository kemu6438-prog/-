## 1. 参考実装の分析: `kexi/tokyo-od-game`

ツイートのリンク（t.co）の転送先は <https://github.com/kexi/tokyo-od-game> **[確認済]**。
「東京都オープンデータ × PLATEAU 3D 都市モデルで 23 区を走る three.js ドライブ探索ゲーム」で、ブラウザで動く。ライセンスは MIT（Copyright (c) 2026 Kei Nakayama）。

### 1.1 構成（package.json より）[確認済]

| 役割 | 使用技術 |
| --- | --- |
| 言語・ビルド | TypeScript / Vite |
| 描画 | three.js（WebGPU 対応、`webgpu-migration.md` あり） |
| 3D 都市データのストリーミング | `3d-tiles-renderer`（3DTilesRendererJS） |
| 物理 | Rapier（`@dimforge/rapier3d-compat`） |
| 道路データ | `@mapbox/vector-tile` + `pbf`（地理院ベクトルタイルのデコード） |
| 標高 | `geotiff`（ビルド時）、地理院 DEM PNG タイル |
| テスト | Vitest + ヘッドレス Chrome での画面検証 |
| 配信 | GitHub Pages（静的ホスティングのみ。サーバ不要） |

つまり**サーバを持たない純フロントエンド**で、データは公共の配信元からブラウザが直接取る構成。この点がこのプロジェクトの最重要の設計判断の参考になる。

### 1.2 データの流れ [確認済: 同リポジトリ knowledge/*.md]

```
建物   PLATEAU 3D Tiles (LOD1, 東京都全域の集約 tileset) ──▶ 3d-tiles-renderer で車の周辺だけ読む
地面   地理院 DEM5A/DEM10B (PNG 標高タイル) ──▶ 地形メッシュ生成 + ジオイド高(EGM2008)を加算
道路   地理院ベクトルタイル experimental_bvmap (z16, road レイヤ) ──▶ 道路グラフ(Worker で構築)
規制   JARTIC(一方通行・速度・横断歩道) と OSM(信号機) ──▶ ビルド時に静的 JSON へ焼き込み
時刻   太陽位置を計算して空・光を決める。天気は気象庁アメダス
```

### 1.3 試行錯誤から得られた重要な知見（自分たちが同じ穴に落ちないために）

1. **建物は LOD2 ではなく LOD1 にした。**
   LOD2（テクスチャ付き）は 1 タイル約 10 MB で、LRU キャッシュ 1.0〜1.6 GB でも満杯になり、表示タイルが 5 枚しか出なかった。中間階層の簡略メッシュが宙に浮く問題もあった。LOD1 は丸の内で 88 MB・表示 68 タイル。
   → **LOD1 + 自前の外壁シェーダー（窓・色・夜の点灯）** が現実解。LOD1 には色が無い。
2. **読み込み範囲を絞らないと破綻する。** 都全域の tileset は遠くの区の粗いタイルまで読んでキャッシュを埋める。`LoadRegionPlugin` で車中心の球（半径 2.8 km、スマホ 1.6 km）に限定した。
3. **浮動原点（floating origin）が必要。** 23 区は端から端まで約 30 km。1 枚の接平面に置くと 15 km 先で 10 m 以上沈む。1.5 km 離れたら原点を付け替える。付け替え時に、窓などの繰り返し模様がずれないよう周期を公倍数にする。
4. **高さの基準が違う。** PLATEAU は WGS84 楕円体高、地理院 DEM は標高（東京湾平均海面）。**ジオイド高（東京で約 34〜40 m）を足して合わせる。** 国土地理院のジオイドモデルを同梱すると測量法の承認が要りうるため、パブリックドメインの EGM2008 を使っている。
5. **DEM5A は平地でも ±1.5 m の凸凹が出る。** 5×5 メディアン + 3×3 フィルタで均している（ガウシアンは盛り上がりが広がるだけで不適）。
6. **地理院ベクトルタイルの道路には、一方通行・信号・車線数・規制速度が入っていない。** 属性は種別（国道/都道/市道）・幅員ランク・高架かどうか程度。そのため参考実装は JARTIC（一方通行・速度規制）と OSM（信号機）をビルド時に対応付けている。
7. **道路網の構築は Web Worker に逃がす。** 計算 120〜140 ms がメインスレッドを止めてカクつく原因だった。Worker 化で最長フレーム 116〜167 ms → 33 ms。ただし結果のメインスレッドへの反映（路面メッシュ生成 約 0.9 秒）が残り、最終的にフレーム分割・資源再利用で改善している。
8. **自動運転は 1,300 行規模。** 法令（信号・一時停止・追い越し・右折の対向車・車間距離・切り返し）まで入れると肥大化する。映像として成立させるには、最初は「車線に沿って走る・信号で止まる・前の車に追従する」で足りる。

### 1.4 参考実装からの「差分」＝ こちらの方針

参考実装は **プレイヤーが運転するゲーム**（物理、違反判定、警察、会話 AI、SNS…）。こちらは **走る映像を見る** ことが主目的なので、次を大きく削れる。

- 手動運転の物理・衝突・転倒復帰 → 不要（まずは）
- 違反判定・取り締まり・ミッション → 不要
- 歩行者との会話・SNS・TTS → 不要
- 代わりに **カメラワーク・景観の質・時間帯と天気の演出・BGM/環境音** に力を入れる

> コードは MIT なので参照は可能だが、**コピーする場合は著作権表示とライセンス文の同梱が必要**。方針としては「設計と知見を参考にして自前で書く」。

## 2. 街のデータをどこから取るか

### 2.1 建物

| 候補 | 内容 | 評価 |
| --- | --- | --- |
| **PLATEAU 3D Tiles LOD1**（採用候補） | 国交省配信。東京都全域の集約 tileset `https://api.plateauview.mlit.go.jp/datacatalog/3dtiles/13-bldg-lod1-latest/tileset.json`（参考実装が使用）。区ごと `13101-bldg-lod1-latest` 形式もある[^plateau-docs] | 無料・サーバ不要・CORS 可（参考実装の記録）。**配信は試験運用で SLA なし**。 |
| PLATEAU LOD2（テクスチャ付き） | 見た目は良いが重い（上記 1.3-1） | 重すぎる。ランドマーク限定の追加用なら可。 |
| Google Photorealistic 3D Tiles | 写真級のメッシュ。1 本の root リクエストで 3 時間分のタイル取得が可能[^google-3d] | 下記 2.4 参照。**ポリシー上の制約が大きい。** |
| OSM の建物フットプリント押し出し | 自前で生成 | 高さ情報が乏しく、PLATEAU に劣る。 |

PLATEAU のデータ一覧は Web API で取れる: `https://api.plateauview.mlit.go.jp/datacatalog/plateau-datasets`（`type_en`、`lod`、`url`、`texture` などのフィールドを持つ）[^plateau-tutorial]。URL は変わりうるので、**ハードコードせず起動時／ビルド時にカタログから引く**設計にする。

### 2.2 道路（形状）

| 候補 | 一方通行 | 信号 | 車線数 | 速度 | 評価 |
| --- | --- | --- | --- | --- | --- |
| 地理院ベクトルタイル `experimental_bvmap`（z4〜16） | × | × | × | × | 形状と幅員ランクのみ。**提供実験・SLA なし**。 |
| OpenStreetMap（Geofabrik 関東抽出 など） | ○ `oneway` | ○ `highway=traffic_signals` | △ `lanes` | △ `maxspeed` | 属性が最も豊富。**ODbL**（帰属表示必須、抽出 DB を公開するなら ODbL）。 |
| JARTIC 交通規制情報 | ○ | – | – | ○ | 参考実装は CORS が無いためビルド時に取得。利用規約は CC BY 4.0 互換（参考実装の記録）。 |
| PLATEAU 道路モデル（tran） | – | – | – | – | LOD2 の歩道部は参考実装が使用。範囲が限定的。 |

**推奨**: 道路ネットワークは **OSM を主**にしてビルド時に静的タイル化（一方通行・信号・車線・速度が最初から揃う）。地理院 DEM で標高を付ける。地理院ベクトルタイルは、必要になったら幅員など補助に使う。
→ 「見る」ゲームで一方通行を逆走する映像は致命的なので、**一方通行を持つデータが最初から要る**。これは参考実装の 道路＝地理院 とは異なる判断。要レビュー（仕様書の未決事項 Q3）。

### 2.3 地形・標高

- 地理院 標高タイル（DEM5A / DEM10B の PNG）。画素の標高値のエンコードを壊さないよう、色変換なしで読む（`createImageBitmap` の `colorSpaceConversion: "none"` など）[確認済: 参考実装記録]。
- 高さ合わせはジオイド高を加算（1.3-4）。
- 地面の色: 地理院シームレス写真 or PLATEAU オルソ（`https://tile.plateauview.mlit.go.jp/tiles/plateau-ortho-2023/{z}/{x}/{y}.png`）[^plateau-terrain]。
  **注意**: 地理院の標準地図と DEM を重ねて立体地図を作る用途は承認申請の対象になりうる（参考実装の法務確認の記録）。地面に使うのは写真系に限定する。
- 代替: PLATEAU-Terrain は quantized-mesh 形式で Cesium 向け[^plateau-terrain]。three.js 側では扱いが面倒なので第一候補にしない。

### 2.4 Google Photorealistic 3D Tiles を使わない理由（現時点）

公式ポリシー[^google-policy]に照らすと:

- 事前取得・保存・キャッシュ・オフライン利用は禁止。**映像の録画・配信機能を作る場合は特に要確認**（Policies に「video creation」の項がある）。
- 画像解析・機械解釈・物体検出などの非可視化用途は禁止 → **自動運転の AI がタイルのメッシュを読んで走る、といった使い方は不可**（道路網は別データが要る）。
- Google ロゴとデータ帰属表示の表示義務、API キー + 課金アカウント必須。
- EEA の請求先では利用できない[^spatialized]。
- 日本の細部（歩道、街路樹）は写実的だが、車載視点では**メッシュの粗さ・歪みが目立つ**。

→ **M0〜M3 では不採用**。将来「リッチ表示モード」として追加する余地は残す（`3d-tiles-renderer` は Google タイルにも対応）。

### 2.5 PLATEAU のライセンス

PDL1.0（CC BY 互換）。出典「国土交通省 PLATEAUウェブサイト」を表示し、**加工した旨**も書く（参考実装の記録: サイトポリシー準拠）。配信は試験運用のため、`-latest` が年度更新で切り替わりスキーマも変わりうる。**tileset の取得失敗時のフォールバック表示を設計に含める。**

## 3. レンダリング

### 3.1 WebGPU の状況（2026-10 時点）[確認済]

- WebGPU は Chrome/Edge（Windows・macOS・ChromeOS は v113〜、Android は v121〜）、Safari 26（2025-09、iOS 含む）、Firefox（Windows v141〜、Apple Silicon Mac）で既定有効。Linux と Firefox Android は未成熟[^webgpu-utsubo]。
- three.js の `WebGPURenderer`（`three/webgpu`）は WebGPU が無い環境で **WebGL 2 に自動フォールバック**する[^webgpu-utsubo]。
- three.js の最新は 0.186.1（npm、2026-10-08 確認）。r183 で `PostProcessing`→`RenderPipeline`、`Clock`→`Timer` に変更あり[^webgpu-utsubo]。**新規コードでは新 API を使う。**

→ **方針**: `WebGPURenderer` + WebGL2 フォールバックで開始。ただしシェーダーは **TSL（three の Shading Language）で書く**（GLSL/WGSL 直書きは避ける。両バックエンドで動く）。TSL・WebGPU 周りは破壊的変更が多いので three のバージョンを固定する。

### 3.2 3D Tiles ストリーミング

- `3d-tiles-renderer` 0.5.3（npm 確認）が three.js 向けの事実上の標準。`LoadRegionPlugin` で読み込み範囲を車中心に限定、LRU キャッシュの上限管理、遠景用の粗い階層だけを別インスタンスで読む手法が参考実装にある。
- PLATEAU の b3dm は Draco 圧縮 + CESIUM_RTC を使う（参考実装の記録）→ DRACOLoader のデコーダ配置が必要。
- 座標は ECEF（地球中心）。ローカル座標（x=東, y=上, −z=北）への変換と浮動原点の管理を自前で持つ。

### 3.3 「映像」としての質を決める要素（このゲームの肝）

LOD1 の建物は灰色の箱なので、見栄えは **シェーダーと光** で決まる。

| 要素 | 手段 |
| --- | --- |
| 外壁 | 建物 ID（頂点属性 `_batchid` / `_feature_id_0`）+ 高さから外壁種別を選び、テクスチャ配列 + 窓マスク |
| 空・太陽 | 実際の日時から太陽位置 → 大気散乱シェーダー or 事前計算スカイ + 環境マップ |
| 夜 | 窓の点灯、街灯、ヘッドライト、ブルーム、路面の濡れ反射 |
| 天気 | 雨粒・フロントガラスの水滴・濡れた路面。必要なら気象庁アメダスで実天気連動 |
| カメラ | 被写界深度、モーションブラー、レンズフレア（過度なら無効化できる設定） |
| 道路表示 | 白線・横断歩道・停止線・矢印。実在データがある範囲だけ正確に |

## 4. シミュレーション（動かす部分）

### 4.1 車の動かし方 — Rapier は最初は不要

参考実装は Rapier で車を剛体として扱う（手動運転・衝突・転倒のため）。**見るだけの自動運転なら次で足りる**。

- 経路（道路グラフ上の車線中心線）に沿う **キネマティック自転車モデル**（前輪操舵・ホイールベース）で位置と向きを更新。
- 路面の高さは地形（DEM）から取り、車体のピッチ・ロールは 4 輪の接地高さから算出。サスの揺れは減衰ばねで演出。
- 利点: 決定論的（同じ seed で同じ映像が再現できる）、軽い、浮動原点の付け替え時に物理世界を作り直す必要がない。
- Rapier は、手動運転モード（M5 以降）を入れる段階で導入する。

### 4.2 自動運転・交通

必要な最小機能（優先順）:

1. 経路探索（A*、一方通行を守る）— 道路グラフの上で目的地まで。
2. 車線追従（先読み距離つきの Pure Pursuit）と曲率に応じた減速。
3. 信号機（OSM の信号位置 → 交差点に寄せ、現示を自動生成）で停止・発進。
4. 前走車への追従（IDM: Intelligent Driver Model）。
5. 交差点での優先関係（まず「信号なし交差点は一時停止して左右確認の演出」程度）。
6. 他の AI 車（背景交通）。数十台。**視錐台外の車は簡易更新**で CPU を節約。
7. 詰まり（スタック）検出と再経路探索・テレポート（映像として不自然な停止を放置しない）。

法令に厳密に従う（追い越し・切り返し・右折の対向車判断…）作り込みは参考実装が膨大に行っている。**映像として破綻しない範囲に絞る**のが方針。

### 4.3 ゲームループ

- **固定タイムステップ**（例 60 Hz）のシミュレーション + 描画（`requestAnimationFrame`）は補間で分離。描画が遅れてもシミュレーションの時間が飛ばない。
- three.js の `Clock` は非推奨になったため `Timer` を使う[^webgpu-utsubo]。
- シミュレーション時間（`simTime`）を一元管理 → 時間帯の加速（1 分で昼夜が巡る等）、一時停止、リプレイ、再現に使う。
- 重い処理（道路グラフ構築、路面メッシュ生成、DEM フィルタ）は Web Worker + フレーム分割（1 フレームの予算 ms を決めて分ける）。参考実装で停止の主因だった（1.3-7）。

## 6. 開発環境の方針（参考実装を踏襲しつつ軽量化）

- Node 24 / pnpm / Vite / TypeScript / Vitest。
- 純粋ロジック（座標変換、グラフ、経路探索、車両モデル、信号）は **DOM/three に依存しない**モジュールにして単体テストする。
- 描画の回帰は **ヘッドレス Chrome でスクリーンショット + FPS/最長フレームのログ**を取って確認（参考実装は QA スクリプトで行っている）。
- アセット（モデル・テクスチャ・データ）は台帳（出典・ライセンス・生成手順）を作る。**ライセンス表記漏れを機械的に検出**できるようにする。
- 巨大データは Git に入れず、`just`/スクリプトでビルド時に生成して `.gitignore`。

- [ ] `13-bldg-lod1-latest/tileset.json` が今日も取得でき、CORS が通る。
- [ ] 地理院 `experimental_bvmap` と `dem_png` の最新の提供状況と URL。
- [ ] 丸の内付近での LOD1 のタイル数・転送量・FPS。
- [ ] 建物 ID の頂点属性名（`_batchid` / `_feature_id_0`）が現行データでも同じか。
